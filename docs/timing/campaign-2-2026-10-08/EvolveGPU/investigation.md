# EvolveGPU interpretation and timing qualification

Both batches completed 256/256 tests successfully. Every evolution fitness and summary generation count matches across runs. Settings-source snapshots and runtime headers match. No missing-test, integrity, success-marker/status, or cumulative-generation discrepancy was found.

Mean successful-solution Duration falls from 1.51015625 to 1.380859375 seconds, an 8.5618% reduction in Run 2. Medians are 1.2 and 1.1 seconds. Run 2 is faster on 185 tests, equal at the 0.1-second logged resolution on 48, and slower on 23. Startup test 0 is retained at 2.1 versus 2.0 seconds, with five generations and identical logged results. The final saved-state application Run durations are 387.778984 and 353.692365 seconds. No cache was cleared or adjusted. A second-launch benefit is observed; cache behavior, initialization, and scheduling are plausible contributors, not demonstrated exclusive causes.

Twelve optimization fitness values differ: tests 12, 17, 44, 50, 86, 99, 109, 168, 169, 215, 218, 242. Exact values are in comparison.json and the all-test CSVs. The implementation uses four asynchronous optimization units and accepts a first qualifying report; `CompleteState` skips subsequent reports after completion. These differences are consistent with arrival-order selection rather than different evolution progress. GPU status logs do not identify every winning candidate's code/registers, so the exact identity explanation cannot be independently proven for all twelve tests. The differences are disclosed, not silently discarded. Test 188's completion fitness prints as 0.00000100 in both runs: the underlying strict threshold check and eight-decimal rounding explain possible boundary ambiguity; all recorded success markers are preserved.

**Timing qualification:** mean Duration/Generation is higher in the later chronological quarters. Quarter means are 0.40010, 0.40318, 0.42202, 0.42170 seconds in Run 1 and 0.37566, 0.37040, 0.38551, 0.38720 in Run 2. The first-to-last quarter increases are about 5.4% and 3.1%. Fitted full-batch changes are +0.03467 and +0.01927 seconds per generation average, with correlations 0.201 and 0.120. Do not describe these GPU batches as perfectly flat.

This simple normalization is not sufficient to isolate environmental drift. Each test searches different seeded code and can perform different optimization work. Quarter mean generation counts increase from 3.40625 to 3.625, and time per generation itself depends on generation-count strata. `timing-investigation.json` preserves an early/late comparison within each stratum. For example, Run 1 two-generation tests average 0.35862 early versus 0.37439 late; three-generation tests average 0.41290 versus 0.41852. Run 2 four- and five-generation strata decrease slightly in the later half. The mix explains part of the sequence effect but does not eliminate all differences. The status optimization-stage median times also show no corresponding monotonic within-run increase.

No continuous clock, temperature, competing-process, cache-hit, or compilation-stage trace was captured while the applications ran. Therefore neither thermal drift nor its absence can be established from the logs. The rise is an explicit qualification of the descriptive timing results; it is not adjusted away, automatically attributed to caching, or used to exclude later tests. The current six batches are complete and no additional test was launched during analysis. A future claim of environmental stability would require additional evidence; this report does not assert it.

High-duration outliers in both runs are tests 16, 21, 50, 56, 74, 88, 118, 122, 131, 157, 172, 191, 201, 231. Their longer times generally accompany more generations; maxima are test 118, 6.4 seconds in Run 1, and test 118, 5.9 seconds in Run 2 (13 generations). All remain included.

Only final test 255 has a saved dense precision value: 0.00002718 in both runs, versus fitness 0.00000080. Thus the fitness success rate is not a demonstrated 1e−6 dense-grid precision success rate. Per-test dense errors and a direct CPU/GPU validation comparison are unavailable in these native logs.
