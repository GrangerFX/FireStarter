# EvolveCPU capability, precision, and timing context

The user explicitly made CPU timing secondary. Both 64-test batches completed with 64 fitness successes and no missing tests. All outer evolution-batch counts match, with mean 5, median 3.5, and range 1–20. This demonstrates that the current algorithm can find solutions meeting its 15-sample Sin fitness target for all configured tests. Dense precision is reported separately; it is not assumed to pass because training fitness passed.

The 256-sample maximum absolute error averages 0.00000450625 in Run 1 and 0.00000522484375 in Run 2; medians are 0.000003195 and 0.00000331. Maxima are 0.00002104 and 0.00002217. Sixty of 64 tests in each run exceed 1e−6 at the printed precision. Four are at or below it: Run 1 [26, 32, 47, 49], Run 2 [26, 32, 47, 48]. Run 2 test 48 prints exactly 0.00000100; the underlying unrounded precision is unavailable. All 64 test values are retained in tests.csv. A 256-point grid is finite validation, not a proof of the maximum error over the continuous interval.

Eight tests select different terminal candidates: 2, 5, 7, 10, 25, 31, 48, 49. Those tests have different winning register arrays, candidate generation counts, fitness, and dense precision. The terminal report lines and register arrays are preserved in each run's terminal-status-rows.json. The implementation dispatches 16 CPU-generated candidate optimizations asynchronously and accepts a qualifying report before later successful reports. The observed different indices/candidate generations with unchanged outer batch counts are consistent with this behavior. For example, test 2's winning report is index 5, generation 5, fitness 0.00000089 in Run 1 versus index 8, generation 6, fitness 0.00000033 in Run 2. Fixed seeds do not guarantee identical final winners in this implementation.

CPU creates `states`, `allStates`, the best state, and the `testedCodes` set inside each test loop. GPU/New similarly initialize test-local state and best-code storage; persistent compilation resources and normal driver caches can intentionally survive between tests. The complete repeated generation sequences and matching settings provide no observed evidence of unexpected evolutionary-state contamination. They do not prove statistical independence or eliminate every possible state bug.

Mean solution times are 27.71875 and 27.8453125 seconds. Their progression is dominated by the number of generations required to find each solution. Both runs have quarter mean generation counts of 3.25, 6.25, 4.5, and 6.0. Run 1's corresponding mean solution times are 17.53125, 34.86875, 25.075, and 33.4 seconds; Run 2's are 18.11875, 34.84375, 25.04375, and 33.375 seconds. The changing search effort explains the apparent slowdown in solution-time averages. It is sampling variation in search difficulty, not evidence that execution progressively slowed.

A descriptive linear fit of each test's rounded Duration against its outer generation count explains 99.978% of duration variance in Run 1 and 99.997% in Run 2, with slopes of 5.56963 and 5.55611 seconds per outer generation. Every test is included. The calculations and quarter means are preserved in [generation-time-relationship.json](generation-time-relationship.json) and reproduced by write-report.py. These fits describe the observed association; they do not isolate the duration of each generation.

A smaller residual observation remains: Run 1's early eight-test mean Duration/outer-generation is 5.32479 seconds, compared with about 5.58–5.60 later; Run 2 remains near 5.57–5.59 throughout. This ratio includes whole-solution work and rounded durations. It should not be conflated with the much larger solution-time variation explained by generation counts, or labeled an established execution slowdown. Optimization-stage status times remain near 5.0 seconds. No concurrent hardware/cache telemetry establishes the cause of the residual, and no environment intervention was made to flatten it. The 0.46% change in overall mean between runs is not a performance conclusion for CPU.

Larger batches would generally smooth sampling fluctuations in mean search effort and solution time. The user's expectation that the apparent drift would become very small at 256 tests is reasonable as an expectation, but its magnitude is not measured here: each configured CPU batch contains 64 tests. No additional tests were performed or extrapolated results substituted for observations.

The descriptive long-duration outliers, 18, 25, 27, 36, 37, 56, 60, 62, are retained. Test 62 is the maximum in both runs: 111.2 and 111.1 seconds over 20 outer batches. One small three-SD generation-average outlier in Run 2 (test 52) occurs in a one-batch search and is sensitive to 0.1-second quantization; it is not a persistent slowdown.
